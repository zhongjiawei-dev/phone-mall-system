# 手机商城 UI 自动化测试计划

## 1. 测试对象

一个本地 Flask 商城站点，包含 8 款手机、3 个测试账号，支持登录、搜索、购物车、结算下单、支付。订单状态只有待支付和已支付，支付成功后扣库存。

## 2. 测试目标

1. 5 条主链路在页面上能完整走通，不依赖手工点。
2. 页面元素变化时，只改页面对象，不改用例。
3. 用例能反复跑，失败后能定位到具体页面和步骤。
4. 已知业务问题用 `xfail` 记录，不写成“通过”。

## 3. 范围

| 做 | 不做 |
| --- | --- |
| 登录、搜索、详情、购物车、结算、订单、支付 | 真实支付、短信、物流 |
| 正常流程和常见异常输入 | 浏览器兼容性矩阵 |
| 库存、金额、折扣、权限的页面表现 | 性能、压测、安全渗透 |
| 单浏览器（Chromium headless） | 移动端适配 |

## 4. 测试策略

- 页面对象模式：每个页面一个类，元素定位符和操作写在页面类里，断言留在测试里。
- 用例互相独立：每条用例前重置数据和登录状态，避免上一条的购物车带进下一条。
- 数据驱动：搜索关键词和预期结果放 YAML，改数据不用动代码。
- 稳定性：统一显式等待，页面跳转后等 URL 或关键元素，不用固定 `sleep`。
- 失败处理：`pytest-rerunfailures` 重跑 1 次，仍失败就截图并附加到 Allure。

## 5. 环境

- Ubuntu 22.04
- Python 3.12.11
- Chromium 146.0.7680.31 + 同版本 ChromeDriver
- Flask 3、Selenium 4.20+
- pytest 9.2、pytest-rerunfailures、allure-pytest

浏览器以 headless 启动，参数里带 `--no-sandbox`、`--disable-dev-shm-usage`，容器里也能跑。

## 6. 准入与准出

准入：站点 `/api/health` 返回 200，3 个账号能登录，8 款商品有库存。

准出：45 条用例执行完；阻断级问题为 0；已知缺陷有 `xfail` 和缺陷单；执行报告里有通过率、耗时和失败截图。

## 7. 风险

- 页面加载慢导致元素还没出现就断言：用显式等待和跳转后的 URL 等待。
- 测试之间共享浏览器进程：每条用例前访问 `/logout` 清登录态，服务端 `/test/reset` 重置商品和订单。
- 站点数据在内存里：测试进程自己起服务，避免和手工开的实例互相影响。
